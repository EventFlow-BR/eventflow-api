# EventFlow v1 database model

PostgreSQL is the authoritative store. Flyway migrations in [db/migration](../src/main/resources/db/migration) define the schema; Hibernate uses `ddl-auto=none` and does not evolve it automatically.

There are **six tables** after V1–V4: four business tables, `processed_messages` for consumer idempotency, and a legacy `tickets` table without an implemented application flow.

## Relationships

```text
users (organizer) 1 --> N events
users (participant) 1 --> N registrations
events 1 --> N registrations
registrations 1 --> 0..1 payments
registrations 1 --> 0..1 tickets [schema only; no v1 flow]

processed_messages [independent message UUID ledger]
```

Business/table IDs use BIGINT GENERATED BY DEFAULT AS IDENTITY, except the message UUID primary key. Timestamps use PostgreSQL TIMESTAMP WITH TIME ZONE and Java OffsetDateTime. Foreign keys have no ON DELETE CASCADE clauses, and no delete endpoints are exposed.

## users

| Column | Definition |
|---|---|
| `user_id` | BIGINT identity primary key |
| `name` | VARCHAR(120), required |
| `email` | VARCHAR(255), required, unique |
| `password_hash` | VARCHAR(255), required; BCrypt output |
| `role` | VARCHAR(20), required; PARTICIPANT or ORGANIZER |
| `created_at`, `updated_at` | Required timestamps, SQL defaults CURRENT_TIMESTAMP |

The application trims/lowercases email before lookup/persistence. The unique email constraint also protects concurrent registration. The database role check allows the two application roles; services/security enforce role-specific actions.

## events

| Column | Definition |
|---|---|
| `event_id` | BIGINT identity primary key |
| `organizer_id` | Required FK to users |
| `name`, `description`, `location` | Required; VARCHAR(150), TEXT, VARCHAR(255) |
| `start_date`, `end_date` | Required timestamps; start must precede end |
| `capacity` | Required INTEGER, CHECK > 0 |
| `price` | Required NUMERIC(10,2), schema CHECK >= 0 |
| `status` | Required VARCHAR(20), default DRAFT; checked values below |
| `published_at` | Nullable timestamp |
| `created_at`, `updated_at` | Required timestamps |

**Schema versus API:** the original price constraint remains `price >= 0`. The v1 creation/update DTOs require **price > 0**, so free events are not supported by the HTTP contract. The schema's broader check is not evidence of a free-event flow.

`published_at` is set on publication and retained after cancellation. Current visibility checks use status and organizer ownership, not this timestamp. There is no automatic FINISHED transition. Future-time eligibility is checked by services at the relevant operation, not by a permanent database check against the current time.

## registrations

| Column | Definition |
|---|---|
| `registration_id` | BIGINT identity primary key |
| `participant_id` | Required FK to users |
| `event_id` | Required FK to events |
| `status` | Required VARCHAR(20); PENDING, CONFIRMED, CANCELLED, EXPIRED |
| `reservation_expires_at` | Nullable in SQL; populated for every current reservation |
| `created_at`, `updated_at` | Required timestamps |

There is **no current unique constraint/index on active participant/event pairs**. V1 created one, but V2 removes it. A pending row may have logically expired before the scheduler changes its status; a status-only partial unique index would incorrectly block a new reservation in that interval.

`RegistrationService` checks duplicates under the Event lock using CONFIRMED or PENDING whose deadline is still in the future. Capacity uses the same definition. These are application/query invariants rather than a time-dependent unique index. Writes bypassing these services are not protected by an independent active-registration uniqueness constraint.

Expiration persists EXPIRED, not CANCELLED. It does not modify a pending Payment, because no Payment is created by reservation.

## payments

| Column | Definition |
|---|---|
| `payment_id` | BIGINT identity primary key |
| `registration_id` | Required unique FK to registrations |
| `amount` | Required NUMERIC(10,2), CHECK > 0 |
| `status` | Required VARCHAR(20); six schema values listed below |
| `created_at`, `updated_at` | Required timestamps |

There is at most one Payment per registration. The current simulation creates APPROVED directly and supports APPROVED → REFUNDED on individual cancellation. Other allowed status values are reserved; a full payment-provider lifecycle is not implemented.

The amount is stored on the payment rather than dynamically derived when reading history. There is no currency column, gateway reference, external settlement, or partial-refund model.

## processed_messages

| Column | Definition |
|---|---|
| `message_id` | Required UUID primary key |
| `processed_at` | Required timestamp |

There is no foreign key to a registration; this is a delivery-processing ledger. `ProcessedMessageRepository.tryInsert()` uses parameterized `INSERT ... ON CONFLICT (message_id) DO NOTHING`. A zero result skips a duplicate. The insert and handler run in one JPA transaction, so handler failure rolls the marker back. No automated retention/cleanup process exists.

## tickets — legacy schema only

The V1 table contains `ticket_id`, unique required UUID `public_id`, unique required FK `registration_id`, `status`, `issued_at`, `created_at`, and `updated_at`. Its allowed statuses are ACTIVE and CANCELLED.

This records historical schema design, not a v1 feature. There is no Ticket entity, repository, service, controller, UUID issuance flow, or message handler issuing tickets. The Java package contains only a placeholder. Existing migrations were not rewritten to remove this unused table.

## Status constraints

| Table | Allowed by current SQL | Produced by current application flows |
|---|---|---|
| users | PARTICIPANT, ORGANIZER | Both |
| events | DRAFT, PUBLISHED, CANCELLED, FINISHED | DRAFT, PUBLISHED, CANCELLED |
| registrations | PENDING, CONFIRMED, CANCELLED, EXPIRED | All four |
| payments | PENDING, APPROVED, FAILED, EXPIRED, CANCELLED, REFUNDED | APPROVED, REFUNDED |
| tickets | ACTIVE, CANCELLED | None |

These are textual columns with CHECK constraints, not PostgreSQL ENUM types. The implemented entity enums reflect their corresponding domain columns; there is no Ticket enum implementation.

## Indexes and audit fields

Explicit non-unique indexes are `events.organizer_id`, `registrations.participant_id`, and `registrations.event_id`. Primary keys and unique constraints additionally index email, payment registration ID, ticket registration/public IDs, and message ID. The removed active-registration index must not be described as present.

Business entity lifecycle callbacks maintain application `created_at`/`updated_at` values. SQL CURRENT_TIMESTAMP defaults initialize timestamps but are not update triggers. `processed_messages` has only `processed_at`; it is not a business entity audit history.

## Migration history

| Migration | Effect |
|---|---|
| `V1__Create_initial_schema.sql` | Creates users, events, registrations, payments, tickets, constraints and initial indexes |
| `V2__Adjust_registration_active_unique_index.sql` | Drops the active participant/event partial unique index |
| `V3__Add_expired_registration_status.sql` | Extends registration status check with EXPIRED |
| `V4__create_processed_messages_table.sql` | Creates the message-id ledger |

The capacity invariant requires transactional Event locking in addition to this schema. See [architecture](architecture.md#transaction-and-concurrency-boundaries) and [business rules](business-rules.md).
